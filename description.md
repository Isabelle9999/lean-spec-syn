Lean-to-Lean Synthesizer

Extract the type signature and look up relevant properties from a built-in table (List → length, membership, permutation; Nat → arithmetic, divisibility, bounds; Array → size, indexing; Option → some/none cases). Scan the function body to classify it: recursive or not, pattern-match or if-else, has termination_by or not, what helper functions it calls, how many arguments it takes. Helpers get spec'd bottom-up, generating specs for inner functions before outer ones, so proved helper properties are available as context. Then ask the LLM what properties should hold about the output, using the type hints and classification as context. If the LLM returns unusable output, right now used as-is.

For spec generation, four strategies run independently, results merged and deduplicated by normalizing variable names. Direct prompting gives the LLM the code, type hints, and exact parameter signature including precondition parameters. Spec-by-example runs the function on real inputs and asks the LLM what pattern connects every input to its output. Negative testing generates wrong outputs and asks for specs that reject them. Generate-with-proof asks the LLM to produce both the theorem and its proof together, directly maximizes the kernel-proved count since the LLM naturally picks specs it knows how to prove. For VERINA benchmarks with known postconditions, the prompt includes the postcondition body and instructs the LLM to prove it and break it into individual conjuncts.

Validation filters specs through a series of checks. First check against a persistent store of known correct and incorrect behaviors from previous runs. Validate any helper definitions the LLM wrote separately, broken helpers are dropped before they contaminate every spec. Typecheck through bare Lean, falling back to Mathlib if bare Lean fails, specs referencing Mathlib definitions like List.Perm need Mathlib to typecheck. If typecheck still fails, feed the error back to the LLM for one retry. Run the function on test inputs to confirm it computes without crashing, constructing precondition proofs automatically with by_decide when needed. Vacuity check replaces the function body with two different wrong implementations, and a spec is only killed if it holds against both, and relational specs where both sides reference the function skip this check to avoid false kills.

Proof search: first only a subset of tactics includes ( ~60) batched into one Lean subprocess call, which go through functional induction, well-founded induction, generalization, backward search with known lemma names, term-mode proofs, proof by contradiction. The function is classified (recursive vs non-recursive, pattern-match vs if-else) to avoid known failure modes like simp looping on recursive definitions. Second step, for specs that bare Lean couldn't prove are batched into one Mathlib call with 120,000+ pre-proved lemmas available, most succeed via rfl where the spec matches an existing Mathlib theorem. Third step, specs that both bare Lean and Mathlib failed go through budget-controlled LLM fallbacks , which is proof sketch with goal-state-targeted hole filling, multi-sample with different strategy hints, blame-repair parsing Lean's error to fix the specific failing subgoal, recursive decomposition into independently proved sub-lemmas, calc-mode equational reasoning, and entailment where if spec A is proved and A implies B is provable then B is proved. Previous failures are included in every retry so the LLM doesn't repeat mistakes.


Then PBT via Plausible, run the spec against random inputs. This only runs on specs that weren't already proved by the automated tactics, so proved specs skip it entirely.


The refinement loop keeps running until no weakness can be found or the iteration budget is exhausted. We measure spec strength by mutation score (fraction of wrong implementations the specs reject). 
Three loops in sequence: 

Loop 1 is mechanical with no LLM, make small changes to the function's code (swap operators, change constants, swap case branches, plus type-directed edits like dropping a list element for list functions or off-by-one for nat functions). Comments and strings are masked so mutations don't produce garbage. Non-compiling mutants are filtered out by typechecking before any evaluation. Each surviving mutant is certified by running both original and mutant on test inputs to confirm they produce different outputs, and only mutants with a proven behavioral difference count. Then if Lean state spec still holds for the wrong implementation, then spec is too weak, and we show the LLM the specific evidence plus all previously accumulated negative examples and it tightens the spec. The strengthened spec re-enters the full validation from the start. We also mutate the spec itself in the opposite direction, this weaken its operators and check if the weakened version still holds, which catches over-specification.

Loop 2 only activate when loop 1 finds nothing: ask the LLM to write a function satisfying all specs but behaving differently, verify both claims mechanically , that the function actually satisfies the specs AND that it diverges from the original. Previous failed attempts are included so the LLM tries different approaches. Three consecutive failures means no loophole found. Loop 3 is entailment and activates only after loop 2 converges: ask the LLM to propose a strictly stronger spec, formally verify the implication is strict, the kernel proves the new spec implies the old but cannot prove the reverse. If found and it passes validation, replace and re-run everything.
